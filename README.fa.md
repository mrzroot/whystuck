# whystuck

**دستورت گیر کرده؟ `whystuck` می‌گوید چرا و به‌جایش چه اجرا کنی.**

هر دستوری را با یک ناظر بی‌حرکتی (idle watchdog) اجرا کن. وقتی دستور ساکت شد، `whystuck` پردازش زنده را بررسی می‌کند و می‌گوید
منتظر چیست: **پیجر**، **ادیتور**، **سؤال y/N**، **پسورد**، **حالت watch**، **قفل** یا **اتصال شبکه‌ای که جواب نمی‌گیرد**؛
یا اصلاً گیر نکرده و فقط یک **سرور** است یا مشغول **محاسبه**. همراه با شواهد و راه‌حل غیرتعاملی.

## مسئله چیست؟

برنامه‌نویس‌ها و ایجنت‌های هوش مصنوعی (مثل Claude Code و Codex و Cursor) هر روز دقیقه‌ها، و گاهی کل یک نشست، را پای دستورهایی که بی‌صدا منتظر می‌مانند از دست می‌دهند:

- `git log` توی `less` می‌ماند؛ `git commit` ادیتور vim را باز می‌کند
- `apt install` و `npm init` منتظر `y` هستند؛ `ssh` منتظر جواب «yes/no» برای کلید میزبان است
- `sudo` و `ssh` و `gpg` روی ترمینال پسورد می‌خواهند
- `vitest` و `jest` در **حالت watch** شروع می‌شوند و هیچ‌وقت تمام نمی‌شوند
- یک سرور توسعه در پیش‌زمینه اجرا می‌شود (که *عادی* است ولی شبیه هنگ کردن به نظر می‌رسد)
- `apt` منتظر قفلی است که پردازش دیگری گرفته؛ `git clone` منتظر اتصالی است که هیچ‌وقت جواب نمی‌گیرد

`timeout` معمولی فقط دستور را می‌کشد و چیزی نمی‌گوید. `whystuck` پیدا می‌کند **منتظر چه چیزی است** و **شکل غیرتعاملیِ** همان دستور را چاپ می‌کند.

## نصب

`whystuck` یک فایل پایتون بدون هیچ وابستگی است (پایتون ۳٫۹ به بالا).

</div>

```bash
git clone https://github.com/mrzroot/whystuck && cd whystuck
pip install .                       # دستور whystuck نصب می‌شود

# یا فقط همان یک فایل را جایی در PATH بگذار
install -m755 whystuck.py ~/.local/bin/whystuck
```

## استفاده

</div>

```bash
whystuck -- git log                        # اگر ۲۰ ثانیه ساکت ماند، تشخیص بده
whystuck --idle 10 --kill -- npm test      # اگر حکم «گیر کرده» بود، دستور را متوقف کن
whystuck --json --kill --idle 15 -- make  # خروجی ماشین‌خوان برای اسکریپت و ایجنت
whystuck --explain 12345                   # پردازشی که از قبل هنگ کرده را بررسی کن (فقط‌خواندنی)
printf 'y\n' | whystuck -- apt-get install jq   # ورودی پایپ‌شده به دستور فرستاده می‌شود
```

<div dir="rtl" align="right">

دستور داخل یک pseudo-terminal اجرا می‌شود و مثل ترمینال خودت رفتار می‌کند. **تشخیص‌ها در stderr** چاپ می‌شوند و stdout فقط خروجی خود دستور است.

| گزینه | معنی |
|---|---|
| `--idle ثانیه` | چند ثانیه بدون خروجی تا تشخیص شروع شود (پیش‌فرض ۲۰). تایپ کردن هم «فعالیت» حساب می‌شود. |
| `--timeout ثانیه` | بعد از این مدت کل دستور متوقف شود؛ `0` یعنی غیرفعال (پیش‌فرض ۶۰۰). |
| `--kill` | وقتی حکم **stuck** بود، دستور (کل گروه پردازش و session) متوقف شود. حکم‌های «گیر نکرده» (server، sleeping، busy) هیچ‌وقت کشته نمی‌شوند. بدون `--kill` فقط گزارش می‌دهد و دستور ادامه پیدا می‌کند. |
| `--json` | یک سند JSON روی stdout چاپ می‌کند. خروجی دستور ضبط می‌شود (۴۰۰۰ نویسه‌ی آخر در `output_tail`) و جاری نمی‌شود. |
| `--stdin pty\|null\|closed` | `pty`: دستور ترمینال دارد (پیش‌فرض). `null`: stdin برابر `/dev/null`. `closed`: stdin بسته. |
| `--explain PID` | پردازش در حال اجرا را بررسی می‌کند (فقط‌خواندنی). بدون متن خروجی آن پردازش، پرسش‌هایی مثل `[y/N]` قابل تشخیص نیستند؛ با `--tail-file` متن را بده. |
| `--demo` / `--rules` | سناریوهای آفلاین / جدول قاعده‌ها |

**کدهای خروج:** `N` وضعیت خود دستور (برای کشته‌شدن با سیگنال `128+سیگنال`)، `124` رسیدن به `--timeout`، `125` تشخیص «گیر کرده» و توقف دستور (`--kill`)، `126`/`127` اجرا نشد/پیدا نشد، `2` خطای استفاده یا سیستم‌عامل پشتیبانی‌نشده.

## برای ایجنت‌های هوش مصنوعی

</div>

```bash
whystuck --json --kill --idle 20 -- <command>
```

<div dir="rtl" align="right">

اگر `exit_code` برابر `125` بود یعنی دستور گیر کرده؛ `verdicts[0].id` و `evidence` و `fixes` را بخوان و دستور را به شکل غیرتعاملی دوباره اجرا کن.
متن آماده‌ی [docs/AGENTS.snippet.md](docs/AGENTS.snippet.md) را در `AGENTS.md` یا `CLAUDE.md` پروژه‌ات بگذار تا ایجنت‌ها از آن استفاده کنند.
به‌عنوان کتابخانه هم می‌شود:

</div>

```python
from whystuck import diagnose

verdict = diagnose(pid, tail=last_terminal_output)   # dict قابل‌تبدیل به JSON، فقط‌خواندنی
if verdict["stuck"]:
    print(verdict["id"], verdict["fixes"][0])
```

## تشخیص چگونه کار می‌کند؟

۱. دستور روی یک PTY اجرا می‌شود؛ whystuck زمان آخرین خروجی و یک «دُم» از خروجی (بدون escape) را نگه می‌دارد و می‌داند ترمینال در alternate screen هست یا نه.

۲. وقتی `--idle` ثانیه هیچ اتفاقی نیفتاد، **یک عکس لحظه‌ای** از درخت پردازش‌ها می‌گیرد. در لینوکس فقط از `/proc` استفاده می‌شود:
`stat` و `cmdline` و `wchan` و **`/proc/PID/syscall`** (یک `read` مسدودشده روی fd که به tty اشاره می‌کند قوی‌ترین نشانه‌ی «منتظر ورودی» است)،
لینک‌های `fd/`، جدول `/proc/net/tcp` (سوکت‌های `LISTEN` و `SYN_SENT`) و یک نمونه‌ی ۰٫۵ ثانیه‌ای از مصرف CPU.

۳. تابع خالص `classify(snapshot)` جدول **مرتب** قاعده‌ها (`RULES`) را می‌گذراند؛ اولین قاعده‌ای که شواهدش موجود باشد برنده است و بقیه به‌عنوان «also matched» می‌آیند.
هر حکم شواهد، راه‌حل و **اطمینان** (low/medium/high) دارد که از تعداد نشانه‌های مستقلِ هم‌نظر محاسبه می‌شود.

۴. اگر هیچ قاعده‌ای نخورد، حکم **`unknown`** با شواهد خام است. هرگز حدس نمی‌زند.

قاعده‌ها: `editor`، `pager`، `secret`، `confirm`، `watch`، `follow` (مثل `tail -f`)، `lock`، `network` (فقط `SYN_SENT`)، `server`، `stdin_wait`، `sleeping`، `busy`، `unknown`. فهرست کامل با `whystuck --rules`.

## محدودیت‌ها (حتماً بخوان)

- **فقط سکوت تشخیص داده می‌شود.** برنامه‌ای که هنگ می‌کند ولی مدام چیزی چاپ می‌کند (spinner یا heartbeat) ساکت نیست و تشخیص داده نمی‌شود.
- **تشخیص پرسش از آخرین خط خروجی** انجام می‌شود. پرسش‌های آزاد مثل `Name?` به‌صورت `stdin_wait` (منتظر ورودی ترمینال، اطمینان متوسط) یا `unknown` گزارش می‌شوند.
- **ادیتور و پیجر با نام پردازش** شناخته می‌شوند (`vim`, `nano`, `emacs`, `less`, `bat`, `delta`, `code --wait`, ...). wrapper با نام دیگر شناخته نمی‌شود.
- **شبکه:** فقط اتصال TCPِ *در حال برقرار شدن* (`SYN_SENT`) تشخیص داده می‌شود. مشکل DNS و اتصال برقرارِ بی‌پاسخ **تشخیص داده نمی‌شوند**. UDP هم نه.
- **`server`** یعنی «یک سوکت TCP در حال listen است و هیچ قاعده‌ی پرسشی نخورد». سرور سالم را از سروری که از درون هنگ کرده تشخیص نمی‌دهد.
- **`busy`** یعنی حداقل ۲۵٪ یک هسته در نمونه‌ی ۰٫۵ ثانیه‌ای. حلقه‌ی بی‌نهایت دقیقاً مثل محاسبه‌ی طولانی دیده می‌شود.
- در کانتینر یا هسته‌های سخت‌گیر ممکن است `/proc/PID/syscall` خوانده نشود؛ whystuck در `notes` می‌گوید و با اطمینان کمتر از `wchan` و متن خروجی استفاده می‌کند.
- **stdin پایپ‌شده:** داده فرستاده می‌شود ولی **EOF نه** (stdin ابزارهای ایجنت اغلب `/dev/null` است و فرستادنش هر پرسشی را به‌جای انتظار، شکست می‌دهد). برای رفتار EOF از `--stdin null` استفاده کن.
- **`--json` آخرین ۴۰۰۰ نویسه‌ی خروجی را شامل می‌شود.** اگر دستورت رمز چاپ می‌کند، در آن هست. *مقدار* متغیرهای proxy هرگز چاپ نمی‌شود (فقط نام).
- راه‌حل‌های پیشنهادی فقط پیشنهادند و از یک جدول کوچک ابزارهای شناخته‌شده می‌آیند؛ قبل از اجرای کار مخرب بررسی‌شان کن.

**پلتفرم‌ها:** لینوکس کامل و تست‌شده در CI (پایتون ۳٫۹ تا ۳٫۱۳). macOS/BSD در حد تلاش: اجرای دستور کار می‌کند ولی شواهد از `ps` و `lsof` می‌آید (بدون syscall و بدون صاحب قفل)؛
در نسخه‌ی ۰٫۱ روی macOS واقعی **تست نشده**. ویندوز پشتیبانی نمی‌شود (پیام روشن می‌دهد و با کد `2` خارج می‌شود؛ از WSL استفاده کن).

## مقایسه با ابزارهای نزدیک

در ۱۸ اکتبر ۲۰۲۶ در GitHub (۸ شکل جست‌وجو)، نام‌های npm/PyPI و وب جست‌وجو شد. **تا اکتبر ۲۰۲۶ ابزار مشابهی پیدا نشد** که مستقل و مستقل از ایجنت باشد، پردازش *زنده‌ی* گیرکرده را بررسی کند و علت + راه‌حل بدهد.
این نتیجه‌ی یک جست‌وجو است نه ضمانت؛ حوزه‌ی ابزار ایجنت‌ها هر هفته تغییر می‌کند و محصولات ایجنت نسخه‌های خصوصی از ایده‌های مشابه دارند. نزدیک‌ترین‌ها:

- [`pi-non-interactive`](https://www.npmjs.com/package/pi-non-interactive): فقط متغیر محیطی را به ابزار bash یک ایجنت تزریق می‌کند؛ پیشگیری است، نه تشخیص.
- [`lukeramsden/pi-prevent-stuck`](https://github.com/lukeramsden/pi-prevent-stuck): فهرست ثابت دستورهای بد داخل یک افزونه؛ بدون بررسی زمان اجرا.
- [قاعده‌ی Majordomus](https://majordomus.dev/rules/project-commands-run-non-interactively-2/) و [CLI Agent Spec](https://agentexperience.tech/checks/axc-c001/): راهنما و قاعده برای نویسنده‌های CLI، نه یک اجراکننده.
- هیوریستیک‌های داخلی ایجنت‌های IDE (مثل [مسئله‌ی ۳۱۳۲۴۴ در VS Code](https://github.com/microsoft/vscode/issues/313244)): داخل یک محصول و غیرقابل استفاده‌ی مجدد.
- [`timeout` گنو](https://www.gnu.org/software/coreutils/manual/html_node/timeout-invocation.html) و `no_output_timeout` در CI: فقط می‌کشند؛ بدون علت و بدون راه‌حل.
